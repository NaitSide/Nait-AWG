# Клиентские экспорты Nait-AWG 0.1.1

Генерация сверена с официальным AmneziaVPN **5.0.3.0**, тег с commit [`de93650a90739b87bb47a632872ea9d0adc9412f`](https://github.com/amnezia-vpn/amnezia-client/tree/de93650a90739b87bb47a632872ea9d0adc9412f). В установленном локально Windows-приложении обнаружена та же версия. В пользовательском протоколе версия экспортировавшего приложения не записана, поэтому это подтверждение выбранной базы исходников, а не доказательство происхождения исходных файлов из данного бинарника.

Проверка относится к структуре экспортов и правилам генерации. Повторные испытания 0.1.1 на Windows, iOS и Android ещё предстоят. Предыдущие 12 успешных сценариев относятся к исходным файлам 0.1.0 и официального приложения. Причина ранее наблюдавшейся проблемы Android не установлена.

## Как клиент использует метаданные

MTU в `last_config` участвует в подготовке соединения даже при отсутствии строки MTU в исходном INI. [`ConnectionController`](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/core/controllers/connectionController.cpp) дополняет отсутствующий MTU значением для своей платформы. Desktop передаёт его как `deviceMTU` через [`localsocketcontroller.cpp`](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/mozilla/localsocketcontroller.cpp); Android читает `mtu` и строковый keepalive в [`Wireguard.kt`](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/android/wireguard/src/main/kotlin/org/amnezia/vpn/protocol/wireguard/Wireguard.kt); iOS строит рабочий INI с MTU и keepalive в [`WGConfig.swift`](https://github.com/amnezia-vpn/amnezia-client/blob/de93650a90739b87bb47a632872ea9d0adc9412f/client/platforms/ios/WGConfig.swift).

Это подтверждает значимость метаданных. Фактический MTU исходных 12 подключений не измеряли. Одинаковое фактическое MTU у `.conf` и `.vpn` либо на разных платформах не заявляется.

Пустые `I2–I5` сохраняются серверным сериализатором, но не попадают в клиентский INI при генерации. `subnet_address` используется при выделении адреса новому клиенту; действующее подключение использует `client_ip`, ключи и endpoint из клиентских метаданных. Само наличие `subnet_address` в гостевом профиле не перенастраивает сервер.

## Настройки новых экспортов

```dotenv
CLIENT_DNS=1.1.1.1, 1.0.0.1
CLIENT_ALLOWED_IPS=0.0.0.0/0, ::/0
CLIENT_PERSISTENT_KEEPALIVE=auto
CLIENT_EXPORT_PLATFORM=desktop
CLIENT_MTU=
```

Настройки применяются при создании нового клиента или при явном переносе из резервной копии. Панель не определяет ОС будущего VPN-клиента по браузеру администратора. Desktop-политика выбрана как явная база для сравнения с Windows-экспортом; для мобильной политики укажите `mobile`, для собственного MTU — числовой `CLIENT_MTU`.

Установщик 0.1.1 записывает эти значения для новой установки. Обновление сохраняет действующий `.env`. Если в нём остались `CLIENT_DNS=1.1.1.1` и `CLIENT_PERSISTENT_KEEPALIVE=25`, это остаются явные настройки новых клиентов, пока администратор сам их не изменит. Изменение этих переменных и перезапуск панели не переписывают уже сохранённые профили.

DNS и MTU, настроенные только в официальном приложении, панель не может получить из одного серверного AWG-конфига. Для сравнения нужны сопоставимые явные настройки. Автоматическое обнаружение контейнера AmneziaDNS и импорт всех настроек официального приложения не добавлены.

## Сохранение и совместимость

Новая запись в `encrypted_config` содержит зашифрованный документ с native-конфигом и гостевыми метаданными. Отдельные файлы с ключами и новая таблица не создаются. Импорт `.vpn` сохраняет MTU, DNS, пустые и отсутствующие поля, версию и остальные поддерживаемые метаданные; меняется только название при выдаче из панели. Дублируемые ключи, адрес, endpoint, порт, маршруты и keepalive проверяются на согласованность. Неизвестные поля отклоняются, а не молча удаляются. Поддерживаются гостевые профили с одним AWG-подключением, без учётных данных администратора.

Записи 0.1.0 остаются прежним текстом внутри шифрования: native-экспорт возвращает те же байты, гостевой — прежние настройки и структуру. При старте нет массовой перегенерации. Если импорт в 0.1.0 уже потерял метаданные `.vpn`, восстановить их из одного сохранённого `.conf` невозможно; 0.1.1 не угадывает утраченный MTU.

После явного редактирования обфускации обновляются оба представления нового профиля; MTU, DNS, адреса и индивидуальные ключи сохраняются. Перенос из резервной копии по-прежнему является отдельным действием с выпуском новых клиентских ключей и конфигов для целевого сервера.

До отката приложения на 0.1.0 следует сохранить состояние, созданное до обновления: старый код не понимает новый документ внутри `encrypted_config`. Автоматическое понижение формата не предусмотрено.

## Проверки

```bash
npm run check
npm test
```

Публичные синтетические фикстуры находятся в `app/services/fixtures/official-5.0.3.0/`; тесты — в `app/services/clientExports.test.js`. Они проверяют полный разобранный эталон, типы и значения полей, native-экспорт, платформенные политики, поколения AWG, реальный путь импорта/экспорта через SQLite, отсутствие переписывания старых записей, обфускацию с журналом и перенос из копии. Для выполнения Bash-сценариев установщика нужен Bash; при его отсутствии эти существующие проверки сообщают о пропуске.

Программные проверки не являются проверкой установки на VPS или подключения реальных устройств.

## План повторного теста на устройствах

Использовать отдельный тестовый сервер и одинаковые применимые DNS/MTU-настройки для официального приложения и панели. Действующие VPS при подготовке этой версии не менялись.

1. Записать точные версии ОС, AmneziaVPN и нативного AmneziaWG; сохранить выбранные DNS и экспортную MTU-политику. Проверить, что до обновления тестовый VPN работает.
2. После установки кандидата 0.1.1 на тестовый сервер проверить прежний профиль без пересоздания: ключи, адрес, DNS и keepalive не должны измениться.
3. Создать независимые официальные и панельные клиенты, получить четыре исходных формата, как в предыдущем тесте. Разобрать экспорты локально и сравнить поля с исключением индивидуальных данных и имени подключения.
4. На Windows, iOS и Android импортировать каждый из четырёх файлов в соответствующее приложение: всего 12 сценариев. Проверить имя подключения, установление туннеля, DNS-разрешение и доступ к интернету, переподключение. Реальное MTU измерить и записать отдельно, если нужно сравнить поведение.
5. Проверить импорт официального `.vpn` в панель и повторную выдачу `.vpn`/QR, в том числе с нестандартным MTU. Затем проверить импорт `.conf` с явным MTU и диапазоном keepalive.
6. На Android сначала использовать исходные имена файлов; если импорт потребует переименования, записать сообщение и проверить укороченное имя. Причина прежнего ограничения имени не установлена.
7. Отдельно проверить QR AmneziaWG и многочастный QR AmneziaVPN. Не публиковать исходные QR и конфиги. Записать результаты и версии приложений; только после этого считать новые функциональные тесты пройденными.

## Клиентские политики

Поверх сохранённого исходного профиля вычисляются общие или персональные I1–I5 и клиентские маршруты. Один результат используется для `.conf`, `.vpn` и обоих QR. Старые профили без новой политики не переписываются при старте. [Модель наследования, перенос, размеры и ограничения](client-policies.md).
